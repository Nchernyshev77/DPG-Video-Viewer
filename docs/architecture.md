# Архитектура

Приложение использует нативные ES-модули. Для статического запуска не нужны
сборщик, фреймворк, серверная часть или npm-зависимости. Node.js используется
для локального сервера, подготовки публикации и тестов.

`app.js` связывает независимые компоненты через события и явные методы.
Модули не обращаются к переменным `window.__...` или к элементам страницы
через неявные глобальные имена.

| Компонент        | Интерфейс                                                                                                    | Ресурсы, которыми владеет                                               |
| ---------------- | ------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------- |
| `Playlist`       | `add`, `select`, `navigate`, `remove`, `clear`; событие `change`                                             | Один object URL на запись                                               |
| `VideoPlayer`    | `load`, `play`, `pause`, `seekTo`, `stepFrames`, `jumpToFrame`; события `ready`, `frame`, `update`, `unload` | Media element, обработчики источника, callback кадра, отмена метаданных |
| `createViewer`   | `setVideo`, `drawFrame`, `pan`, `setFov`, `reset`, `clear`                                                   | Renderer, камера, геометрия, материалы, текстура, ResizeObserver        |
| `createHUD`      | `update`, `cancelEdit`                                                                                       | Редактирование номера кадра и обновление времени/FPS                    |
| `createPanels`   | `render`, `updateActive`, `close`, переключатели                                                             | DOM плейлиста, положение панелей и обработчики                          |
| `createAutoHide` | `refresh`, `show`                                                                                            | Таймер скрытия и восстановления курсора                                 |
| `bindInput`      | Привязывает UI к методам компонентов                                                                         | Горячие клавиши, pointer/drag/drop/fullscreen, таймер клика             |

У каждого компонента есть `dispose()`. `createLifecycle()` снимает DOM- и
Three.js-обработчики, отменяет AbortSignal и выполняет локальные cleanup-функции.
Это позволяет повторно создавать viewer в большом приложении без накопления
слушателей.

## Загрузка и память

Добавление файла создаёт object URL непосредственно из `File`. Само видео
при добавлении ещё не читается. Каждый экземпляр записи, включая повторное
добавление одного файла, имеет собственный URL для прямого доступа.

`VideoCache` предзагружает только выбранный файл, если его размер не превышает
выбранный лимит (по умолчанию 2 GiB). Один отменяемый `FileReader` читает
весь файл в ArrayBuffer; из него создаётся один плоский `Blob`, как в исходной
версии. Кешированная копия не зависит от исходного диска. Метаданные затем
читаются из неё; имя и дата исходного файла сохраняются для парсера. Созданным
URL владеет кеш, а не запись плейлиста. Ключом служит объект исходного File;
совпадение имени/размера/даты не смешивает разные файлы.

LRU ограничивает суммарные байты завершённых кешированных файлов; вытеснение
происходит перед чтением нового файла. URL текущего источника отключается до
вытеснения. `prune()` сохраняет только файлы оставшихся записей; повторные
записи одного объекта File используют копию до удаления последней записи.
Ошибки предзагрузки и превышение лимита возвращают прямой доступ. Это кеш
закодированных данных, а не декодированных кадров; браузер может разместить
Blob в RAM или во временном локальном хранилище. Его служебная память и память
декодера/GPU не входят в лимит кеша. Во время создания Blob одновременно
существуют ArrayBuffer и копия данных: пиковая память может превышать лимит.

При переключении сначала отключаются старые callbacks и слушатели, renderer
освобождает текстуру, затем сбрасывается старое media element. Новый источник
получает новое video element и номер поколения. Асинхронный результат
метаданных и предзагрузки применяется только к своему поколению. Переключение
источника прерывает и сетевое чтение, и callbacks. Изменение лимита кеша
перезагружает источник с сохранением позиции и намерения проигрывания.

Подготовка первого кадра принимает `loadeddata`, `canplay`, `canplaythrough`,
progress, seeked и проверку readyState по таймеру только во время загрузки.
Условие готовности: readyState >= HAVE_CURRENT_DATA, ненулевые размеры и
завершённый seek. `preload=auto` является подсказкой браузеру; если через
750 мс после метаданных кадра нет, muted play активирует декодер. При обычном
открытии видео затем приостанавливается и восстанавливает исходную позицию.
Ручная кнопка Start video передаёт намерение воспроизведения до готовности.

Каждый источник имеет deadline 45 секунд. Ошибка/тайм-аут кешированной копии
отключает старое media element и один раз пробует оригинальный URL; неудачная
копия освобождается. Вторая ошибка завершает loading и показывает повтор.
Кнопка прямого открытия отменяет FileReader, но сохраняет лимит кеша.
FileReader имеет timeout 60 секунд без прогресса, обновляемый progress-событиями;
отмена отклоняет Promise даже если браузер не отправил событие abort.
Все timers принадлежат lifecycle источника и отключаются при готовности,
ошибке, переключении и dispose. `diagnostics()` хранит не более 24 событий.

MP4-парсер просматривает заголовки контейнера, пропускает `mdat` по размеру и
читает только данные `hdlr`/`mdhd`/`stts`. Он ограничен 4 MiB чтения и 4096
заголовками, понимает 64-битные размеры атомов и `mdhd` v0/v1. Для WebM/MKV
читается не более 1 MiB начала файла; `DefaultDuration` берётся только из
видеодорожки. Если метаданные не поддерживаются, повреждены или превышают
бюджет, воспроизведение продолжается, а FPS оценивается по предъявленным
кадрам при проигрывании.

## Рендеринг

Во время воспроизведения renderer рисует на каждом `requestAnimationFrame`,
как исходная версия. Задержка или отсутствие `requestVideoFrameCallback`
не останавливает обновление текстуры: callbacks служат для оценки FPS и HUD,
причём обновления интерфейса ограничены интервалом 80 мс. Media element
остаётся вне DOM, как в исходной версии; видимым изображением владеет WebGL.
На паузе seek, движение камеры и resize запрашивают отрисовку по необходимости,
а несколько запросов за один экранный кадр объединяются. Постоянного render
loop на паузе нет.

Очередь seek удерживает блокировку после `seeked`, пока `readyState` не станет
не ниже HAVE_CURRENT_DATA и Promise от `viewer.drawFrame()` не подтвердит
фактическую перерисовку WebGL. Это не позволяет следующему seek лишить renderer
видеокадра до загрузки текстуры. Пока видео seeking или readyState < 2, renderer
сохраняет последний кадр. Обычная перемотка объединяет запросы до последней
позиции; автоповтор кадров хранит только одно направление. Keyup, pointerup,
blur и смена источника останавливают повтор. Позднее подтверждение renderer
старого поколения не может выполнить seek в новом ролике.

Вращение на паузе оставляет damping OrbitControls: следующие перерисовки
вызываются только пока камера движется. WebGL context loss отображается
пользователю; после восстановления обновляется текстура и размер viewport.
360° сфера создаётся только когда впервые нужен этот режим.

## Развитие

Сборка размещает src/styles/vendor в общей папке assets с fingerprint по
содержимому. Относительные импорты модулей и import map остаются внутри той
же версии. HTML переключается на новую папку целиком; предыдущую публикацию
assets можно сохранять для вкладок, открытых до обновления.

Новый источник (изображения, последовательность кадров или удалённое видео)
можно реализовать отдельным контроллером с теми же событиями `ready`, `frame`,
`update`, `unload`. Поддержку другого рендера можно добавить за интерфейсом
viewer. Рабочие реализации предпочтительнее неиспользуемых адаптеров с TODO.

Текущая таблица DOM подходит для обычных плейлистов; выбор ролика обновляет
только старую и новую активную строку. Для тысяч записей следующим шагом будет
виртуализация списка. Сборщик имеет смысл добавлять при измеренной потребности
в tree shaking, объединении большого числа модулей или TypeScript.
